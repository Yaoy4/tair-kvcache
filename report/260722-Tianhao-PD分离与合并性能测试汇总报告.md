# HiSim PD 分离与 PD 合并性能测试汇总报告

**模型：** Qwen/Qwen3-8B（FP16）  
**目标设备：** RTX PRO 6000 Server  
**后端：** AIC e0735ccca08c790b37c511a20f484a62a4127118  (SGLang 0.5.10)  
**测试方式：** HiSim CPU Simulation + AIConfigurator  
**测试日期：** 2026-07-21 至 2026-07-22  
**状态：** PD 合并、PD 分离及 P/D 拓扑扩容测试均已完成

---

## 1. 执行摘要

本报告将原始测试结果统一整理为 **PD 合并** 和 **PD 分离** 两类。两类测试共用的模型、后端、请求生成方式和主要性能指标集中列在报告前部；各实验仅说明拓扑、并行度、缓存开关、代码版本等差异。

### 核心结论

| 测试方向 | 主要结果 | 结论 |
| --- | --- | --- |
| PD 合并 TP 扩展 | TP=2/4/8 相对 TP=1 的 E2E 几何平均加速比分别为 **1.419×、1.553×、1.694×** | 增大 TP 整体有效，但加速明显低于资源增长比例，扩展效率逐步下降 |
| PD 分离对称 TP 扩展 | P/D 均从 TP=1 扩至 TP=2/4，E2E 几何平均加速分别为 **1.535×、1.796×** | P、D 两侧同步扩 TP 可稳定改善全部 18 个公共测试单元 |
| PD 分离副本扩展 | 同规模比较中，扩 D 在 96 组对比中的 **80 组** E2E 更低，整体快 **1.467×** | 当前 workload 下 Decode 是更普遍的瓶颈，应优先评估 D 副本扩容 |
| Radix cache 开关 | 短请求 E2E 基本稳定，部分重负载 case 的 TTFT、TPOT 变化明显 | 缓存开关会改变调度行为，重负载结论必须在相同 cache 条件下比较 |
| P/D 扩容边界 | `IL=4096、RR>=8` 的 16 组对比中 P 扩容约快 1%–2% | “优先扩 D”是总体策略，不是所有 workload 的无条件结论 |

> **总体建议：** decode-heavy、长输出或低 RR 长服务时间场景优先增加 D replicas；需要同时降低 Prefill 和 Decode 计算时间时，再考虑 P/D 两侧同步增加 TP。单独增加 P replicas 在本次矩阵中收益很弱。

## 4. PD 合并测试结果

### 4.1 测试范围

PD 合并使用 `disagg.enabled=false`、`DP=1`，测试：

1. TP=1、TP=2，分别比较开启和禁用 radix cache。

### 4.2 TP 扩展汇总

以下统计使用禁用 radix cache 的 18 个公共 cell，以 TP=1 为基线。由于 TP=1/2 与 TP=4/8 来自不同 HiSim commit，TP=4/8 的加速比用于观察整体趋势，不作为严格的同版本扩展效率结论。

### 4.3 Radix cache 影响

- TP=1 的 `IL=1K, OL=1K` 场景，禁用 cache 后 E2E 仅增加约 0.03%–0.09%。
- TP=1 的 `IL=4K, OL=1K` 场景，E2E 变化约为 +0.14%、-0.82%、-0.75%。
- 重负载下调度更敏感。例如 TP=1、`RR=1, IL=4K, OL=4K` 的 TTFT 增加 68.37%，E2E 增加 16.56%。
- 部分 case 出现 TTFT 增大但 TPOT 降低，最终 E2E 反而下降，说明不能仅看单一指标判断 cache 效果。

### 4.4 PD 合并结论

1. 增大 TP 可以稳定降低整体 E2E，TP=8 在本矩阵中覆盖面最好。
2. TP 从 1 增至 8，资源增加 8 倍，但 E2E 几何平均仅加速 1.694×，存在明显的非计算瓶颈和并行效率损失。
3. 长输入场景中 TPOT 不一定随 TP 单调下降，尤其 `IL=16K` 时需要同时观察 TTFT、TPOT 和 E2E。
4. Radix cache 对短请求影响较小，但会改变重负载调度结果；所有横向对比必须统一 cache 条件。

## 5. PD 分离测试结果

### 5.1 对称 TP 扩展

该组测试保持 P、D 两侧 TP 相同，使用 `disagg.enabled=true`、`DP=1` 和 `--disable-radix-cache`。

| P TP=2 / D TP=2 | 1.535× | 18 / 18 |

### 5.4 扩展性

| 扩容方向 | 2 到 16 副本 E2E 几何平均加速 | 改善 cell | 最佳 workload | 最佳加速 |
| --- | ---: | ---: | --- | ---: |
| Prefill：`2P1D` 到 `16P1D` | 0.987× | 4 / 24 | RR=64, IL=1,024, OL=1,024 | 1.035× |
| Decode：`1P2D` 到 `1P16D` | 1.259× | 12 / 24 | RR=1, IL=8,192, OL=1,024 | 3.146× |

最大同规模差距出现在 `16P1D` 对 `1P16D`、`RR=1, IL=8192, OL=1024`：E2E 从 138,847.17 ms 降至 19,059.93 ms，D 扩容快 7.285×。

例外全部集中在 `IL=4096、RR=8/64`。这些场景中 P 扩容约快 1%–2%，接近 P/D 平衡区，不能仅凭该小幅模拟差异决定部署。

### 5.5 PD 分离结论

1. P/D 两侧同步增加 TP 能稳定改善公共矩阵中的全部 cell。
2. 固定副本总规模时，增加 D replicas 在 83.3% 的对比中获得更低 E2E，说明 Decode 是本次 workload 更普遍的容量瓶颈。
3. Prefill replicas 从 2 增至 16 基本没有整体收益，继续单侧堆 P 副本不是高效方案。
4. Decode replicas 扩容具有负载选择性，主要收益集中在长输出、低 RR 或请求服务时间较长的场景。
5. 长 IL 与长 OL 同时存在时，单侧扩容容易受到另一侧瓶颈限制，应评估 P、D 同时扩容。

## 6. PD 合并与 PD 分离横向分析

### 6.1 可直接确认的共同趋势

- 两种模式下，提高计算并行度均能降低大多数 workload 的 E2E。
- 随 TP 或副本规模增加，加速低于线性，调度、排队、KV 传输和另一阶段计算会逐步成为瓶颈。
- `OL=4096` 对 Decode 资源更敏感；只增加 Prefill 资源通常无法解决长输出负载。
- 高负载下 TTFT 和 TPOT 可能向相反方向变化，部署判断应以 E2E、吞吐和服务目标共同决定。

### 6.2 当前数据不能严格证明的内容

现有结果不能直接给出“PD 合并一定快于 PD 分离”或相反结论，原因包括：

1. 两组测试跨越不同 HiSim commit。
2. 部分 PD 合并基线未禁用 radix cache，而 PD 分离测试统一禁用。
3. PD 合并主要测试 TP 扩展，PD 分离拓扑报告主要测试 replicas 扩展，资源含义不同。
4. PD 分离包含 KV transfer、双阶段排队和不同 queue mode，不能只按 TP 或设备数做简单等价。

因此，本报告将两类结果用于各自模式内的扩展性判断，不把跨版本的小幅数值差异作为模式优劣结论。

---

## 7. 最终结论与部署建议

1. **PD 合并：** TP 扩展有效但收益递减。若目标是简单拓扑和稳定降低延迟，可从 TP=2 或 TP=4 开始评估；TP=8 虽覆盖全部 cell，但资源效率较低。
2. **PD 分离：** 当前矩阵中 Decode 是主要扩容方向。同等副本规模下优先增加 D replicas，尤其适用于长输出和低 RR 长服务时间场景。
3. **Prefill 扩容：** 单独从 2P 增至 16P 几乎无整体收益。只有确认线上瓶颈位于 Prefill 排队或 TTFT 后，才应增加 P replicas。
4. **双侧扩容：** 长 IL + 长 OL 场景以及需要同时改善 TTFT、TPOT 的场景，应考虑 P/D 同时增加 TP 或 replicas，避免单侧扩容后被另一侧限制。
5. **缓存条件：** Radix cache 开关必须作为正式测试维度记录。重负载下它会显著改变调度和 TTFT，禁止混合 cache 条件计算加速比。
6. **上线前复测：** 应使用同一 commit、同一 cache 设置和真实流量长度分布，在真实 RTX PRO 6000 上复测候选拓扑。

---

## 8. 结果解释边界

- 本报告结果来自 HiSim CPU simulation 与 AIC 预测，不等同于真实 GPU 端到端测量。
- 每个 cell 固定 `seed=1`，没有覆盖多随机种子波动。
- `random-range-ratio=1`，未覆盖真实线上输入长度分布。
- 每个 cell 主动 flush cache，且多数后续实验禁用 radix cache，不代表有前缀复用的线上场景。
- 副本扩容报告没有 `1P1D` baseline，只能比较同规模 P/D 资源方向和 2 到 16 副本的相对扩展性。
- 跨 workload 汇总采用几何平均；容量规划仍应优先查看与线上流量最接近的单 cell。
